۱. خلاصه مدیریتی پروژه (Executive Summary)

این پروژه به منظور بررسی عملی و کمّی مفاهیم همانندسازی داده‌ها (Replication)، مدل‌های سازگاری (Consistency Models) و موازنه‌های هندسی تئوریک مانند قضیه CAP در سیستم‌های توزیع‌شده پیاده‌سازی شده است. سیستم توسعه داده‌شده یک Replicated Key-Value Store توزیع‌شده شامل ۳ نود سرور مستقل (Replica) است که با زبان Go (Golang) پیاده‌سازی شده و از طریق HTTP REST API با کلاینت و نودهای همتا ارتباط برقرار می‌کند.

ویژگی‌های کلیدی پیاده‌سازی:
  • پشتیبانی دوگانه از مدل‌های سازگاری: پشتیبانی کامل از Eventual Consistency (غیرهمگام AP) و Strong Consistency (همگام CP بر پایه Quorum).
  • مدیریت نسخه و حل تعارض: الگوریتم Last-Write-Wins (LWW) با برچسب زمان دقت نانوثانیه و شناسه سرور (Replica ID).
  • اتوماسیون تست تجربی: اجرای ۱۸ سناریوی تست خودکار تحت تاخیرهای مختلف شبکه (0ms, 500ms, 2000ms) و شبیه‌سازی خرابی نودها.

۲. مفاهیم نظری و تئوریک رایانش توزیع‌شده (Theoretical Foundations)

۲-۱. انگیزه همانندسازی (Replication Drivers)

در سیستم‌های توزیع‌شده، همانندسازی به چهار علت اساسی انجام می‌پذیرد:

  1. دسترس‌پذیری بالا (High Availability): در صورت خرابی یک سرور، سایر سرورها به درخواست کلاینت‌ها پاسخ می‌دهند.
  2. مقیاس‌پذیری و کاهش تاخیر خواندن (Performance & Scalability):** توزیع بار درخواست‌های خواندن (GET) روی سرورهای متعدد.
  3. تحمل خطا و ماندگاری داده (Fault Tolerance & Durability):** جلوگیری از بین رفتن داده‌ها بر اثر خرابی سخت‌افزاری.
  4. کاهش تاخیر جغرافیایی: قرار دادن داده‌ها نزدیک به کاربران جغرافیایی مختلف (CDNs).

۲-۲. قضیه CAP و اثبات منطقی آن

طبق قضیه CAP (Brewer's Theorem)، در زمان بروز تفکیک شبکه (Partition - P)، یک سیستم توزیع‌شده نمی‌تواند همزمان هم Consistency (C) و هم Availability (A) کامل را تضمین نماید.

Network Partition (P) [Client 1] ---> (Replica A) x (Replica B) <--- [Client 2] PUT x=10 GET x=?

در دیاگرام فوق، قطع ارتباط بین A و B مانع از ارسال پیام همگام‌سازی می‌شود. سرور B باید بین دو گزینه انتخاب کند:

  • گزینه ۱ (AP - Eventual Consistency):** پاسخ دهد و داده قدیمی را برگرداند $\rightarrow$ نقض Consistency.
  • گزینه ۲ (CP - Strong Consistency):** پاسخ ندهد یا خطا برگرداند $\rightarrow$ نقض Availability.

۴. تشریح دقیق و خط‌به‌خط کدها (Exhaustive Code Breakdown)

۴-۱. کد سرور همانندساز (codes/replica/main.go)

ساختارهای داده اصلی به صورت زیر در Go تعریف شده‌اند:

type DataEntry struct {
    Key       string `json:"key"`
    Value     string `json:"value"`
    Version   int    `json:"version"`     // شماره نسخه تک‌نوا
    UpdatedBy string `json:"updated_by"`  // شناسه سرور بروزرسانی‌کننده
    Timestamp int64  `json:"timestamp"`   // زمان نانوثانیه‌ای سیستم برای LWW
}

type Replica struct {
    config    Config
    data      map[string]DataEntry
    mu        sync.RWMutex               // قفل خواندن/نوشتن چندنخی
    client    *http.Client               // کلاینت HTTP برای ارسال به سایر Peerها
    isRunning bool                       // پرچم وضعیت سرور
}

توابع کلیدی پردازش PUT و Quorum اکثریت:

func (r *Replica) replicateStrong(entry DataEntry) bool {
    totalNodes := len(r.config.Peers) + 1
    majorityNeeded := totalNodes/2 + 1 // برای ۳ نود برابر ۲ است
    acknowledged := 1 // تایید نود محلی

    var wg sync.WaitGroup
    var ackMu sync.Mutex

    for _, peer := range r.config.Peers {
        wg.Add(1)
        go func(peerURL string) {
            defer wg.Done()
            if r.sendReplication(peerURL, entry) {
                ackMu.Lock()
                acknowledged++
                ackMu.Unlock()
            }
        }(peer)
    }
    wg.Wait()
    return acknowledged >= majorityNeeded
}

۷. پرسش و پاسخ‌های دفاع (Q&A Defense Guide)

سوال ۱: اگر در مدل Strong یکی از سرورها خاموش شود چه می‌شود؟
پاسخ: حد نصاب اکثریت برای ۳ نود برابر ۲ نود است ($3/2 + 1 = 2$). تا زمانی که ۲ سرور روشن باشند، PUT موفق خواهد بود. اگر ۲ سرور خاموش شوند، عملیات شکست می‌خورد تا Consistency حفظ شود.
سوال ۲: چالش اصلی الگوریتم LWW چیست؟
پاسخ: انحراف ساعت سرورها (Clock Skew). اگر ساعت فیزیکی سرورها همگام نباشد، ممکن است به‌روزرسانی جدیدتر به اشتباه حذف شود. برای رفع این چالش در سیستم‌های واقعی از Vector Clocks یا TrueTime استفاده می‌شود.
